# 第二十三章：从 BMAD-METHOD 学到的架构模式

> "可复用的设计模式胜过具体实现"
>
> — 工程智慧

---

## 引言

BMAD-METHOD 不只是一个工具，更是一组**可复用的架构模式**。

本章将这些模式提炼出来，方便你应用到自己的项目中——无论你做的是 AI 工具、传统软件还是任何其他系统。

每个模式包含：
- **场景**：何时使用
- **解决方案**：如何实现
- **示例**：BMAD 中的应用
- **变体**：其他可能的实现

---

## 模式 1：渐进式披露（Progressive Disclosure）

### 场景

系统功能复杂，但不能一次性展示给用户，否则会淹没他们。

### 解决方案

**分层披露**：
- L1：核心信息（90% 用户需要）
- L2：详细信息（10% 用户需要）
- L3：完整内容（深度使用时需要）

**触发机制**：
- 用户主动询问
- 系统检测到需要
- 渐进式上下文加载

### BMAD 中的应用

**Skill 加载机制**：

```
SKILL.md（小，<5KB）
  ↓ AI 阅读全部
  ↓ 决定需要什么
references/
  ├── detailed-rules.md     # 仅在需要时加载
  ├── examples.md
  └── advanced-patterns.md
```

**优势**：
- LLM 上下文不爆炸
- 按需深入
- 性能好

### 你的应用

**示例 1：API 文档**
- L1：快速开始（5 分钟）
- L2：常用功能（30 分钟）
- L3：完整 API 参考（按需）

**示例 2：用户引导**
- L1：核心功能介绍
- L2：高级技巧（用户主动）
- L3：API/SDK（开发者）

## 模式 2：约定优于配置（Convention over Configuration）

### 场景

系统需要灵活，但完全自由会让用户迷失。

### 解决方案

**默认行为**：
- 90% 场景符合约定
- 10% 场景可覆盖

**约定层次**：
- 命名约定
- 目录结构
- 配置默认值

### BMAD 中的应用

**目录约定**：

```
模块结构（强约定）：
my-module/
├── module.yaml          # 必需，固定名
├── skills/              # 必需，固定名
│   └── skill-name/
│       └── SKILL.md     # 必需，固定名
```

**用户无需选择**：
- 把 Skill 放哪里？→ skills/
- 文件叫什么？→ SKILL.md
- 元数据写哪？→ frontmatter

**结果**：
- 学习成本低
- 工具可自动化
- 一致性高

### 你的应用

**示例 1：项目脚手架**
- 标准目录（src/, tests/, docs/）
- 标准文件（README.md, package.json）
- 用户开箱即用

**示例 2：测试框架**
- 测试文件命名约定（*.test.js）
- 自动发现
- 无需手动注册

## 模式 3：分层覆盖（Layered Override）

### 场景

需要支持团队规范和个人偏好共存。

### 解决方案

**层次堆叠**：
```
L1（默认） → L2（团队） → L3（用户） → L4（高级）
```

**合并规则**：
- 后层覆盖前层
- 同时保留所有层
- 用户可以追溯来源

### BMAD 中的应用

**四层配置**：

```python
config = merge(
    installer_config,    # L1
    team_config,         # L2
    user_config,         # L3
    custom_user_config   # L4
)
```

**实际效果**：
- 团队统一规范
- 个人保留偏好
- 不需要 fork

### 你的应用

**示例 1：编辑器配置**
- L1：默认配置
- L2：项目 .editorconfig
- L3：用户全局配置
- L4：用户项目配置

**示例 2：CI/CD 配置**
- L1：模板默认
- L2：组织策略
- L3：项目配置
- L4：分支特定配置

## 模式 4：声明式优于命令式（Declarative over Imperative）

### 场景

定义"做什么"比定义"怎么做"更稳定、可读、可复用。

### 解决方案

**声明式**：
- 描述目标状态
- 系统决定如何达到
- 配置驱动

**对比**：
```yaml
# 声明式
platforms:
  claude-code:
    target_dir: .claude/skills

# vs 命令式
function installClaude() {
  mkdir(".claude/skills");
  copy("SKILL.md", ".claude/skills/");
}
```

### BMAD 中的应用

**platform-codes.yaml**（声明式）：

```yaml
github-copilot:
  installer:
    target_dir: .agents/skills
    commands_target_dir: .github/agents
    commands_extension: .agent.md
    transform: skill-to-agent
```

**优势**：
- 新增平台无需写代码
- 配置易审查
- 可以代码生成

### 你的应用

**示例 1：基础设施**
- Terraform（声明式）
- vs Shell 脚本（命令式）

**示例 2：UI**
- React JSX（声明式）
- vs jQuery（命令式）

## 模式 5：失败安全（Fail-Safe）

### 场景

系统操作可能失败（网络、磁盘、用户输入）。

### 解决方案

**多层保护**：
1. 输入验证（事前）
2. 事务式操作（事中）
3. 自动回滚（事后）
4. 备份恢复（兜底）

### BMAD 中的应用

**安装器的事务**：

```javascript
async install() {
  const backup = await this.snapshot();
  
  try {
    await this.doInstall();  // 在 staging 区域
    await this.commit();     // 原子移动
  } catch (error) {
    await this.rollback();   // 自动回滚
    await this.restore(backup);  // 恢复备份
    throw error;
  }
}
```

**用户感知**：
- 操作失败 → 系统恢复原状
- 不会"半成品"
- 信任感强

### 你的应用

**示例 1：数据库迁移**
- 备份 → 迁移 → 验证 → 提交/回滚

**示例 2：文件操作**
- 写入 .tmp → 验证 → 原子重命名

## 模式 6：哲学化的强约束

### 场景

AI 系统倾向于"礼貌偏差"，需要反向激励。

### 解决方案

**强制规则**：
- 必须做 X
- 零 X 触发暂停
- 提供逃生通道（解释原因）

### BMAD 中的应用

**对抗式审查**：

```markdown
你**必须**找到问题。
零发现触发暂停——重新分析或解释原因。
```

**效果**：
- AI 无法"懒惰肯定"
- 强制深入分析
- 提升发现率

### 你的应用

**示例 1：代码审查 AI**
- 必须找出 N 类问题
- 零发现触发重审

**示例 2：创意生成**
- 必须提供 3 个不同方向
- 不允许"安全"答案

## 模式 7：人机协作的检查点

### 场景

AI 自动化与用户控制的平衡。

### 解决方案

**关键节点暂停**：
- AI 完成阶段性工作
- 系统暂停，要求用户确认
- 用户可调整或继续

### BMAD 中的应用

**Quick Dev 工作流**：

```
1. AI 解析需求
   ⏸️ [用户确认意图]
2. AI 生成规格
   ⏸️ [用户批准规格]
3. AI 编写代码
4. AI 审查代码
   ⏸️ [用户最终决策]
```

**优势**：
- 用户保持控制
- 错误早发现
- 信任建立

### 你的应用

**示例 1：AI 写作助手**
- 大纲 → [确认] → 草稿 → [确认] → 终稿

**示例 2：自动化部署**
- Build → [确认] → Staging → [确认] → Production

## 模式 8：透明的状态追踪

### 场景

用户需要理解系统当前状态。

### 解决方案

**外化状态**：
- 状态存为文件（非内存）
- 文件可读
- 用户可审计

### BMAD 中的应用

**files-manifest.csv**：

```csv
type,name,module,path,hash
skill,"BMad Help",core,core/bmad-help/SKILL.md,e3b0c44...
```

**用户可以**：
- 直接查看安装清单
- Git 追踪变化
- 手动验证完整性

### 你的应用

**示例 1：工作流状态**
- .workflow-state（YAML）
- 用户可中断、查看、恢复

**示例 2：缓存元数据**
- cache.json（明文）
- 易调试

## 模式 9：可逆性优先

### 场景

任何"不可逆"操作都让用户紧张。

### 解决方案

**所有操作可逆**：
- 删除 → 移到回收站
- 修改 → 备份原版
- 安装 → 可卸载

### BMAD 中的应用

**`bmad uninstall`**：
- 完全清理
- 恢复修改
- 删除生成文件

**用户心理**：
- "万一不喜欢可以卸载" → 敢于尝试
- "可以回滚" → 敢于升级

### 你的应用

**示例 1：CMS**
- 文章修改 → 版本历史
- 删除 → 回收站

**示例 2：数据库**
- 软删除（is_deleted 字段）
- 而非硬删除

## 模式 10：策展 + 开放

### 场景

生态需要质量保证 + 创新自由。

### 解决方案

**三层结构**：
- 核心：严格策展
- 扩展：松散策展
- 私有：完全开放

### BMAD 中的应用

**模块系统**：
- 官方模块（core, bmm, tea）：核心团队维护
- 社区模块：作者负责
- 自定义模块：用户私有

**用户根据信任度选择**。

### 你的应用

**示例 1：插件系统**
- 官方插件（认证）
- 社区插件（用户评分）
- 私有插件（企业内部）

**示例 2：内容平台**
- 编辑精选
- 社区贡献
- 用户私域

## 模式 11：组合优于继承

### 场景

复杂功能的实现方式选择。

### 解决方案

**小组件组合**：
- 每个组件单一职责
- 通过组合构建复杂功能
- 避免深层继承

### BMAD 中的应用

**Skill 组合**：

```
完整工作流 = 多个 Skills 组合

PRD 工作流：
  → Mary: bmad-brainstorming
  → John: create-prd
  → Winston: review-architecture
```

**没有"超级 Skill"**，只有小 Skill 的组合。

### 你的应用

**示例 1：UI 组件**
- 小组件（Button, Input）
- 组合成复杂组件（Form）

**示例 2：微服务**
- 单一职责服务
- 通过 API 组合

## 模式 12：事件驱动的进度反馈

### 场景

长时间操作需要用户感知进度。

### 解决方案

**事件流**：
- 业务逻辑发布事件
- UI 订阅事件
- 解耦但同步

### BMAD 中的应用

**安装器**：

```javascript
installer.on('progress', (data) => {
  ui.updateBar(data.percent);
  ui.setMessage(data.message);
});

installer.on('warning', (data) => {
  ui.showWarning(data.text);
});

installer.on('complete', () => {
  ui.showSuccess();
});
```

**优势**：
- 业务逻辑不关心 UI
- UI 可替换（CLI/GUI）
- 易测试

### 你的应用

**示例 1：上传进度**
- onProgress / onComplete / onError

**示例 2：构建系统**
- 各阶段事件
- 实时显示

## 应用建议

### 何时使用这些模式

**全部模式都适用的场景**：
- 开发者工具
- AI 辅助系统
- 复杂工作流系统

**部分模式适用的场景**：
- 简单 CRUD：模式 2、4、5、9
- 数据系统：模式 5、8、9
- 内容系统：模式 7、9、10

### 模式之间的关系

```
                       渐进式披露 (1)
                            ↓
约定优于配置 (2)  ←→  组合优于继承 (11)
        ↓
分层覆盖 (3)  ←→  声明式 (4)
        ↓
失败安全 (5)  ←→  事件驱动 (12)
        ↓
强约束 (6)  ←→  人机检查点 (7)
        ↓
透明状态 (8)  ←→  可逆性 (9)
        ↓
                       策展+开放 (10)
```

**模式互相强化**：
- 透明状态 → 可逆性容易
- 失败安全 → 用户敢尝试
- 约定 → 组合容易

## 设计原则提炼

从这些模式中，可以提炼出一个元原则：

> **设计模式服务于用户体验，而非展示技术**

**核心思想**：
- 模式不是装饰
- 模式解决具体问题
- 用户体验是最终标准
