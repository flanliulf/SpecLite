# 附录 D：分析方法论

本附录记录了生成本书的分析方法论，让读者理解"这本书是怎么写出来的"。

---

## 概述

本书基于 **source-to-gitbook** 方法论，通过"理解 → 结构化 → 叙事化"三阶段递进模型，从 BMAD-METHOD 源码中提取设计哲学。

**核心思想**：
> 源码不仅是功能的实现，更是设计决策的物化。
> 每一行代码都是一个"是"——选择了这个方案。
> 每一个被省略的功能都是一个"否"——拒绝了那个方案。
> "是"和"否"的集合构成了项目的设计哲学。

---

## 阶段一：全景扫描（理解）

### 目标
建立对项目的完整认知地图。

### 执行方式
并行启动 5 个探索 Agent，分别从不同维度切入：

#### Agent 1：项目结构与技术栈（骨架）
- 目录树、package.json/requirements.txt
- 模块划分、代码行数统计
- 外部依赖数量和类型
- 构建/测试/部署配置

**输出**：
- 目录树（ASCII 格式）
- 技术栈清单（表格）
- 代码量统计（81,332 行）
- 依赖清单（13 个核心依赖）

#### Agent 2：核心存储与处理模块（心脏）
- 核心数据结构和主要算法
- 入口点追踪（bmad-cli.js）
- 关键路径（从输入到输出）

**输出**：
- 入口点清单（CLI 命令）
- 核心数据结构（Installer、Manifest、Config 类）
- 数据流图（ASCII 文本图）
- 关键算法摘要（哈希计算、CSV 解析）

#### Agent 3：数据处理管道（消化系统）
- 数据摄入/转换/标准化
- 格式处理与编码
- 性能关键路径和瓶颈

**输出**：
- 数据管道全景图（输入 → 转换 → 存储 → 检索）
- 格式处理清单（YAML、CSV、Markdown）
- 存储层架构（文件系统）
- 性能关键路径（三大瓶颈）

#### Agent 4：接口与集成（皮肤）
- API 设计风格（无 REST API）
- CLI 命令结构
- 配置系统与扩展点
- 外部集成方式

**输出**：
- 接口清单（CLI、Skills、配置文件）
- API 设计模式分析（Skill-first）
- 配置系统架构（四层 TOML）
- 外部集成清单（GitHub、Git、npm）

#### Agent 5：文档与叙事（作者的自述）
- README 中的项目愿景和主张
- 基准测试和性能声明
- CHANGELOG 中的演进历史
- 已知问题和诚实声明

**输出**：
- 项目愿景摘要（人类增强而非替代）
- 核心价值主张（5 个要点）
- 性能声明清单（无量化基准）
- 演进历史时间线（V1.0 → V6.6）
- 诚实声明清单（误报率、收益递减）

### 汇总输出
- 模块清单（42 个 Skills）
- 数据流图（安装流程、Skill 执行）
- 核心创新点（5 个）
- 不确定点清单（5 个待验证问题）

## 阶段二：设计决策提取（结构化）

### 目标
从代码中提取**设计决策**，而非仅仅是功能描述。

### 五层追问框架

对每个关键模块/每行重要代码：

| 层次 | 问题 | 含义 |
|------|------|------|
| **What** | 它做了什么？ | 功能层 |
| **Why** | 它为什么这样做？ | 决策层 |
| **What NOT** | 它没有做什么？ | 取舍层 |
| **Alternatives** | 被拒绝的替代方案？ | 设计空间层 |
| **Cost** | 这个选择的代价？ | 诚实层 |

### 分析示例

**模块**：四层配置系统

```
What？     → 四层 TOML 配置合并（installer → team → custom → user）
Why？      → 解决"标准化 vs 定制化"矛盾
What NOT？ → 没有 GUI 配置界面、没有配置验证器
Alternatives？ → 单层配置、环境变量、数据库存储
Cost？     → 学习曲线、调试难度、文档负担
```

### 设计原则提炼

从决策矩阵中识别反复出现的模式：

1. **简单透明优于复杂高效**（CSV、文件系统、Markdown）
2. **人类增强优于自动化**（具名 Agent、引导式协作）
3. **标准化与定制化并存**（四层配置、固定 Agent + 可定制行为）
4. **质量优于速度**（对抗式审查、拒绝时间估算）
5. **开发者友好优于用户友好**（Git、CLI、TOML）

**统一原则**：尊重开发者、尊重约束、尊重真相、尊重协作

## 阶段三：叙事建构（叙事化）

### 目标
将离散的设计决策编织成连贯的设计哲学叙事。

### 叙事框架

每一章的内在逻辑：

```
1. 定义问题（为什么这个问题重要）
2. 列出约束（设计空间有多大）
3. 展示决策（源码中的具体选择）
4. 提供证据（基准数据或逻辑论证）
5. 承认代价（诚实地指出取舍）
```

### 全书结构规划

```
问题空间 → 为什么这个问题存在
核心架构 → 项目的关键设计决策
数据管道 → 技术实现的深入分析
质量保障 → 对抗式审查机制
工作流设计 → 规模自适应、引导式协作
扩展与集成 → 模块生态、跨平台适配
性能与权衡 → 三大瓶颈、拒绝量化基准
设计原则 → 提炼的五大原则和架构模式
```

### 章节写作标准

每章遵循统一结构：

1. **开篇引言**：源码注释或核心观点（引用块）
2. **问题定义**：为什么这个话题重要
3. **约束分析**：设计空间有多大（表格对比）
4. **源码实现**：3-5 行关键代码 + 深度解释（2-3 处/章）
5. **验证与证据**：数字锚定论点
6. **诚实陈述**：承认局限或代价
7. **章末过渡**：引导到下一章（斜体）

**写作原则**：
- 每章 100-200 行 Markdown
- 源码引用密度：2-3 处/章
- 数字锚定：具体数字替代模糊描述
- 诚实度审计：承认局限，不美化不回避

## 五大分析模式

### 模式 1：约束倒推法

**核心思想**：不是从功能出发，而是从约束出发理解设计。

**执行步骤**：
1. 列出项目的所有硬约束
2. 推导这些约束排除了什么
3. 分析约束空间内剩下的可行方案
4. 验证项目是否选择了该路径

**应用案例**：CSV 选择
- 约束：零依赖、人类可读、Git 友好
- 排除：SQLite（二进制）、JSON（diff 不友好）
- 可行方案：CSV、YAML
- 验证：项目选择 CSV

### 模式 2：隐喻-实现同构分析

**核心思想**：检验项目的概念隐喻是否真的对应代码实现。

**执行步骤**：
1. 识别项目使用的核心隐喻
2. 在源码中逐一查找对应实现
3. 验证映射关系（1:1 映射 vs 营销包装）
4. 分析映射中的不一致

**应用案例**：具名智能体
- 隐喻："AI 即队友"（Mary、John、Winston）
- 实现：6 个具名 Agent，可定制行为
- 映射：1:1 映射（隐喻即架构）

### 模式 3：What NOT 分析法

**核心思想**：分析代码中"没有"什么，往往比分析"有"什么更能揭示设计哲学。

**执行步骤**：
1. 列出该类型项目通常会有的功能
2. 逐一检查本项目是否实现了这些功能
3. 对于每个"缺失"：刻意省略 vs 尚未实现 vs 能力不足
4. 将"刻意省略"归类为设计原则的证据

**应用案例**：
- CSV 没有：索引、JOIN、事务 → 设计声明："简单透明优于复杂高效"
- Skills 没有：类型检查、单元测试 → 设计声明："为 LLM 优化，而非为开发者优化"

### 模式 4：数字锚定法

**核心思想**：用具体数字把抽象哲学锚定到可验证的事实。

**执行步骤**：
1. 收集项目中所有可量化的数据点
2. 将抽象描述替换为具体数字
3. 为每个数字标注来源

**应用案例**：
- ❌ "代码量精简" → ✅ "81,332 行代码"
- ❌ "技能丰富" → ✅ "42 个 Agent Skills"
- ❌ "跨平台支持" → ✅ "40+ AI IDE 平台"

### 模式 5：诚实度审计

**核心思想**：将项目自己承认的错误作为分析的锚点。

**执行步骤**：
1. 搜索项目中的诚实声明（Known Issues、Limitations）
2. 对每个诚实声明分类（设计取舍 vs 实现缺陷）
3. 将"诚实"本身提炼为分析维度
4. 在书中专设"诚实笔记"章节

**应用案例**：
- 对抗式审查的误报率
- 收益递减的承认
- 时间估算禁令的原因

## 质量标准

### 源码引用密度
- 每章 2-3 处源码引用
- 每处 3-5 行关键代码 + 深度解释
- 严禁整段粘贴超过 10 行的代码

### 数字锚定
- 每个重要论点至少有一个具体数字支撑
- 数字必须有明确来源（文件名 + 行号，或基准测试名称）

### 诚实度
- 承认每个设计选择的代价
- 指出可能的反对意见
- 标注不确定性

### 章节长度
- 每章 100-200 行 Markdown
- 全书 15-25 章，3000-5000 行
