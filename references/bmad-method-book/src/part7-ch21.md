# 第二十一章：为什么拒绝量化性能基准

> "我们删除了 33 个工作流中的所有时间估算"
>
> — CHANGELOG V5.x

---

## 一个反直觉的选择

打开任何 AI 工具的营销页面，你会看到：

- "**10 倍**开发速度"
- "节省 **80%** 时间"
- "比传统方式快 **5 倍**"

**BMAD-METHOD 的选择**：**拒绝**这些声明。

更进一步：在 V5.x 时代，BMAD 主动**删除**了所有工作流中的时间估算。

这不是营销失误，而是深思熟虑的设计哲学。

## 问题定义：基准的虚假

### 问题 1：基准的不可比较

**典型营销声明**：
> "使用我们的工具，开发速度提升 10 倍。"

**真相**：
- 10 倍 vs 什么？
- 谁的开发？
- 什么任务？
- 什么质量？

**实际情况**：
```
任务 A（简单 CRUD）：10x 速度提升
任务 B（复杂业务逻辑）：1.2x 速度提升
任务 C（创新设计）：可能更慢
任务 D（调试 legacy）：完全不适用
```

**结论**：单一数字掩盖巨大方差。

### 问题 2：质量被忽略

**速度 vs 质量**：

```
基准 1：5 分钟生成 100 行代码
基准 2：30 分钟生成 100 行代码

哪个更好？
```

**取决于**：
- 代码质量
- bug 数量
- 可维护性
- 是否符合需求

**简单结论**：速度数字本身无意义。

### 问题 3：用户技能差异

**同一工具，不同用户**：

| 用户类型 | 完成时间 |
|---------|---------|
| **新手** | 3 小时 |
| **中级** | 1 小时 |
| **专家** | 30 分钟 |

**基准取哪个**？
- 新手：放大效果（适合营销）
- 专家：缩小效果（接近真实上限）
- 平均：意义不大（分布偏斜）

### 问题 4：场景特异性

**完全不同的场景**：

```
场景 A：新项目，从头开始
  → AI 工具效果最佳

场景 B：维护 legacy 代码
  → AI 工具效果有限

场景 C：探索性研究
  → AI 工具可能误导

场景 D：高度定制业务逻辑
  → AI 工具帮助有限
```

**单一基准**忽略了场景多样性。

## BMAD 的诚实选择

### 选择 1：删除时间估算

**V5.x CHANGELOG**：
> "删除了 33 个工作流中的所有时间估算。AI 速度不可预测，估算误导用户。"

**之前**：
```markdown
## Create PRD

预计时间：30 分钟

[工作流步骤]
```

**之后**：
```markdown
## Create PRD

[工作流步骤]
```

**理由**：
- AI 速度因模型、提示、用户而异
- 估算不准 → 用户失望
- 不估算 → 用户根据实际调整预期

### 选择 2：拒绝速度声明

**BMAD 不会说**：
- ❌ "10 倍开发速度"
- ❌ "节省 80% 时间"
- ❌ "比 X 工具快 N 倍"

**BMAD 会说**：
- ✅ "提供结构化工作流"
- ✅ "强制对抗式审查"
- ✅ "降低认知负担"

**关键差异**：
- 不承诺速度
- 强调价值

### 选择 3：质量优先的指标

**BMAD 关注的"基准"**：

1. **完整性**：是否覆盖关键步骤
2. **质量**：审查发现的问题
3. **可维护性**：代码可读性
4. **正确性**：是否符合需求

**这些指标**：
- 难以量化
- 但更接近真相

## 设计哲学：诚实优于营销

### 原则 1：不可量化的不要量化

**例子**：
- "代码质量" → 不量化
- "用户满意度" → 不量化
- "节省时间" → 不量化

**为什么**：
- 量化迫使简化
- 简化扭曲真相
- 真相比数字重要

### 原则 2：可量化的诚实量化

**例子**：
- ✅ "支持 40+ 平台"（事实）
- ✅ "包含 42 个 Skills"（事实）
- ✅ "代码 18,342 行"（事实）

**这些数字**：
- 客观可验证
- 不涉及"提升""节省"
- 用户可以独立判断

### 原则 3：承认不确定性

**典型 BMAD 表述**：

```markdown
## 预期效果

对于不同规模项目：
- Level 0：节省时间不明显（任务太小）
- Level 1-2：通常有效（具体程度因项目而异）
- Level 3-4：效果显著（但学习曲线陡）

我们不承诺具体百分比。
你的体验可能不同。
请自行试用并评估。
```

**关键**：
- 区分场景
- 承认变异
- 邀请验证

## 诚实陈述：诚实的代价

### 代价 1：营销劣势

**问题**：
- 没有"10x 速度"等吸引眼球的数字
- 在与其他工具比较时显得"不自信"
- 营销文案难写

**实际影响**：
- 增长可能慢
- 投资人可能不感兴趣
- 用户初次接触时印象平淡

**接受**：
- 慢但真实的增长
- 用户基于真实价值留存
- 长期建立信任

### 代价 2：用户期望管理

**问题**：
- 用户问"能省多少时间？"
- BMAD 答："我们不知道，取决于你的项目"
- 用户可能不满意

**实际场景**：
```
用户："用 BMAD 开发能快多少？"

BMAD 回答（诚实）：
"我们不能给你具体数字。原因：
1. 取决于项目复杂度
2. 取决于你的熟练度
3. 取决于代码质量要求

建议：在你的小项目上试用，
亲自评估是否值得采用。"

用户反应：
- 50% 觉得"靠谱"
- 30% 觉得"含糊"
- 20% 离开
```

**取舍**：宁可失去 20%，保留 80% 的真实信任。

### 代价 3：竞争压力

**问题**：
- 竞争对手可能"虚报"数字
- 用户对比时 BMAD"输"
- 销售场景困难

**实际影响**：
- B2B 销售吃亏
- "为什么不像 X 工具那样有数据"
- 难以进入"采购清单"

**应对**：
- 提供试用而非 PPT
- 让用户实际体验
- 建立 case study（带方法论）

## 反例：当性能基准成为陷阱

### 案例：某 AI 编程工具的"10x"声明

**声明**：
> "使用 X 工具，开发速度提升 10 倍"

**真相**（基于研究）：
- 在简单 boilerplate 任务：3-5x（不到 10x）
- 在复杂业务逻辑：1.2-1.5x
- 在调试任务：可能慢 1.5x（误导）
- 在长期维护：质量问题导致总成本增加

**用户反馈**：
- 初期兴奋（被 10x 吸引）
- 中期失望（实际效果远不如）
- 长期反感（质量问题暴露）

**结果**：
- 初期增长快
- 用户流失严重
- 品牌信任受损

**BMAD 的选择**：避免这个陷阱。

## 替代评估方法

如果不用速度基准，如何评估 BMAD 的价值？

### 方法 1：试用 Pilot

**流程**：
1. 选择一个真实小项目
2. 用 BMAD 完成
3. 自己评估

**评估维度**：
- 完成度
- 质量
- 流程感受
- 团队协作

### 方法 2：对照案例

**Case Study 格式**：

```markdown
## Case Study: ACME 公司 CRM 项目

**项目规模**：Level 3
**团队**：5 人
**周期**：3 个月

**使用 BMAD 的体验**：
- ✅ PRD 完整度高
- ✅ 架构决策有据可查
- ⚠️ 学习曲线 1-2 周
- ❌ 部分场景过于流程化

**ROI（团队评估）**：
- 节省返工时间：明显（具体数字依赖团队）
- 提升代码质量：显著
- 团队对齐度：很高

**是否推荐**：是（适合 Level 2+ 项目）
```

**特点**：
- 真实场景
- 多维度
- 不掩盖局限

### 方法 3：开源透明

**任何人可以**：
- 阅读源码
- 试用工具
- 验证声明
- 提出质疑

**这是最高的诚实**：
- 不需要相信营销
- 不需要相信数字
- 自己看，自己判断

## 设计原则提炼

从拒绝量化基准中，可以提炼出一个核心原则：

> **诚实建立长期信任**

**具体体现**：

1. **不承诺无法验证的数字**
2. **承认场景特异性**
3. **承认用户差异**
4. **邀请用户验证**

**统一思想**：
- 短期营销劣势
- 长期信任优势
