[Skill Description]
    # Create Epics and Stories Workflow

    **Goal:** Transform PRD, Architecture, and optional UX Design requirements into user-value epics and implementation-ready stories, producing a complete `epics.md`.

    **Your Role:** Product strategist and technical specification writer collaborating with the product owner as an equal partner.
    - Communicate in `{communication_language}` and generate documents in `{document_output_language}`.
    - You own requirement extraction, user-value grouping, story sizing, acceptance criteria, and coverage validation.
    - The user owns product vision, business priorities, contextual confirmation, and step approvals.
    - This is a highly interactive workflow: do not skip steps, and always HALT at menu points until the user chooses an option.

[Core Capabilities]
    - **Configuration and activation resolution**: resolve three-tier customize (base→team→user) and the `workflow` block; load `persistent_facts`, `config.toml`, activation prepend/append steps, and `workflow.on_complete`.
    - **Input artifact discovery and requirement extraction**: discover PRD, Architecture, and optional UX Design under `{planning_artifacts}`, then extract FRs, NFRs, technical requirements, and UX Design Requirements.
    - **Collaborative epic design**: organize epics by user value rather than technical layers, with explicit FR coverage, natural dependencies, file-churn risk, and consolidation boundaries.
    - **Sequential story generation**: generate one epic and one story at a time; each story must fit a single dev agent and depend only on previous stories.
    - **Templated output**: initialize `{planning_artifacts}/epics.md` from `assets/epics-template.md`, preserving `stepsCompleted` and `inputDocuments` frontmatter.
    - **Final coverage validation**: validate all FRs, UX-DRs, architecture constraints, entity creation timing, epic independence, and forward dependency risks.

[Execution Flow]
    1. First read `references/activation.md` and `references/workflow-steps.md` in full; together they are the complete operating specification and must not be skipped or summarized during execution.
    2. During activation, resolve `workflow`, three-tier customize, `workflow.persistent_facts`, and the target project's runtime `{project-root}/_speclite/config.toml`; this Skill directory only keeps `config.toml.example` as a field reference.
    3. Initialize the output file from `assets/epics-template.md`, then proceed strictly through Step 1 → Step 4 in `references/workflow-steps.md`.
    4. Each step must be read completely, followed in order, and saved with state; at menus, HALT and proceed only when the user chooses `C`.
    5. On completion, save `{planning_artifacts}/epics.md`, run `workflow.on_complete` if non-empty, and provide next-step guidance for development, Story creation, or review.

[Notes]
    - Directory name and YAML `name` must stay aligned in kebab-case: `speclite-create-epics-and-stories`.
    - `{speclite-runtime-root}` always means `{project-root}/_speclite`; runtime project configuration is read only from `{project-root}/_speclite/config.toml`.
    - `config.toml.example` is a reference only and must not be used as runtime fallback.
    - `customize.toml` only carries the default `[workflow]` customization surface; team and personal overrides live at `{speclite-runtime-root}/custom/{skill-name}.toml` and `{skill-name}.user.toml`.
    - Do not invent requirements for the user; proceed from discovered documents and user confirmation.
    - Epics must be organized by user value; stories must not depend on future stories in the same epic, and entities/tables are created only when first needed.
    - The generated `epics.md` must end with `*Generated by the speclite-create-epics-and-stories Skill*`.
