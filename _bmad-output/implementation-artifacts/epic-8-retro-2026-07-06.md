## Executive Summary（执行摘要）

Epic 8 完成了 9 个 Story，把 SpecLite CLI 的 human-readable output 从“各命令各自拼装文案”推进为一套 outcome-oriented presentation system。核心交付包括 shared presentation frame、install / update / repair / status / validate / resolve 的 human-only outcome、`zh-CN` / `en-US` message catalog、path-safe Next Actions、docs / fixture coverage matrix、presentation profile taxonomy、scan-friendly layout 和受控 ANSI color helper。

本 Epic 的最大价值不是“输出变好看”，而是把用户能否理解当前结果、写入边界、问题影响和下一步动作变成可测试契约。实现过程中多次证明：只测 synthetic renderer 不够，必须覆盖真实 command branch、CLI surface、docs option parity、JSON contract stability 和 no-color / CI / non-TTY 边界。

主要风险也集中在系统边界：human output 只能是 presentation layer，不能扩展 public JSON contract；message catalog 与 command-specific Next Actions 需要明确 ownership；build / packaging gate 可能产生 manifest drift；mixed worktree 中的 unrelated canonical package roots 会污染 fixture baseline。Epic 8 最终通过 strict CR closeout，但这些经验需要带入 Epic 9 和后续 ecosystem work。

## What Worked（有效实践）

- **Contract-first output design（契约优先的输出设计）**: 先定义 outcome taxonomy、section semantics、human-only boundary，再实现 renderer，避免把 prose 变成 automation contract。
- **Real branch regression（真实分支回归）**: Story 8.2、8.4、8.5、8.8、8.9 都说明真实 command / CLI branch 测试比 renderer-only 测试更可靠。
- **Scope boundary discipline（范围边界纪律）**: Epic 8 没有把 Epic 7 的 Post-MVP commands 自动纳入范围，保持了 corrective Epic 的聚焦。
- **Docs as checked surface（文档作为受检表面）**: Story 8.7 通过 option parity test 把 CLI reference 从人工说明升级为可验证 surface。
- **Accessibility and portability（可访问性与可移植性）**: `NO_COLOR`、CI、non-TTY、docs fixture 和 JSON no-ANSI 边界进入测试，而不是依赖人工记忆。

## Problems and Fixes（问题与修复）

- **Resolve contract ambiguity（Resolve 契约歧义）**: Epic SR Round 1 发现 Story 8.5 的 `unresolved` human outcome 可能冲突默认 missing-key pure JSON contract。修复方式是明确 `--human` opt-in，默认 machine mode 不变。
- **Partial failure missing AC（部分失败缺少验收）**: Story 8.3 最初缺少 `partial-or-failed` AC。修复后把 partial execution、safe-write、operation-lock 和 failed step evidence 写入 AC 与 tests。
- **Status mapping drift（Status 映射漂移）**: Story 8.4 最初没有 `highLevelHealth` 到 human outcome 的 deterministic mapping。修复后 `stale` / `unknown` 被限制为 human-derived label。
- **Synthetic test blind spot（合成测试盲区）**: Story 8.2 的真实 prewrite branch 漏掉 Next Actions；Story 8.5 的 source path 展示也需要真实 resolver evidence。修复方式是增加 command-level focused tests。
- **Path and empty-state ownership（路径与空态归属）**: Story 8.8 暴露 `../noi` basename 退化和非 issue 空态混入 `Issues`。修复后保留 raw relative target 并保持 `Issues` section 语义纯净。
- **Environment guard precedence（环境禁色优先级）**: Story 8.9 暴露 `NO_COLOR` / CI 可被 explicit false options 绕过。修复后真实环境禁色高于 options。

## Next Epic Preparation（下一 Epic 准备）

Epic 9 聚焦 installed runtime activation contract hardening。Epic 8 对 Epic 9 的直接输入包括：

- `speclite resolve config/customization` 的 default machine contract 已被 Story 8.5 保护，Epic 9 可以把它作为唯一默认 activation resolver。
- Story 8.5 已反复暴露默认 `python3` 缺少 `tomllib` 的兼容问题，Epic 9 需要避免把 Python resolver 继续写成默认 activation path。
- human output 与 machine output 的分层经验可复用于 Epic 9：安装态 skill activation 应消费 stable JSON，而不是 human prose。
- docs / fixture / packaging drift 的处理经验需要进入 Epic 9 full corpus gate，避免 installed skill corpus 看似通过但遗漏 `SKILL.en.md`、references 或 mirror surface。

### Preparation Gates（准备门禁）

1. **Resolver Contract Gate（Resolver 契约门禁）**: Epic 9 Story 9.1 必须先证明 canonical installed skills 使用 `speclite resolve`，不回退 Python resolver 或单文件 `_speclite/config.toml`。
2. **Corpus Coverage Gate（语料覆盖门禁）**: full corpus scan 必须覆盖 `SKILL*.md`、references、terminal steps、installed mirror 和 support-side negative scan。
3. **Compatibility Asset Gate（兼容资产门禁）**: Python resolver scripts 只能作为 compatibility / troubleshooting assets，不得重新成为 default resolver。
4. **Fixture Boundary Gate（Fixture 边界门禁）**: 遇到 unrelated package root count drift 时先隔离范围，再决定是否刷新 baseline。
