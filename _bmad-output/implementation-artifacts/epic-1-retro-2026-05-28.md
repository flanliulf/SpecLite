### Challenges（挑战）

- Epic 1 初始验收更偏向 representative fixture 与最小阶段入口，后来才由 sprint change proposal 明确 full canonical skill closure 属于 MVP 安装基线。
- Story 1.3 曾暴露 final pre-write summary 与最终 selected module set 不一致的风险；Round 5 才确认最终 summary 绑定 `finalSelectedModules`。
- Story 1.5 / 1.6 的风险集中在 installed inventory 与 readiness gate：help/phase rows 不能替代完整 package root inventory，ReadyCheck 也不能只看 required entries。
- 多轮 reviewer 记录披露当前环境缺少独立 `Agent` 调度工具，CR 只能按 skill fallback 在主上下文串行覆盖三层视角。
- 当前仓库没有 `lint` script；部分 CR 记录把 `npm run lint` 的 Missing script 明确判定为项目事实，而非当前 Story 缺陷。
- `project-context.md` 仍是 placeholder，不能被当作完整 discovery 后的权威上下文。

### Key Lessons（关键经验）

1. Full canonical package root inventory 是安装完整性事实；help/menu/phase rows 只是 discovery projection。
2. Final pre-write install scope summary 必须在最终 selected modules 和 config plan 确定后生成，且必须发生在 project writes 前。
3. ReadyCheck 必须消费 selected module package roots、skill index、IDE mirror visibility 与 target skill count，而不是只看少数 required entries。
4. Public JSON contract 不应为局部实现方便而增加 `readySummary`、`failedStep`、`changedPaths` 或临时 summary blob。
5. Corrective reopen 已完成 Story 的时候，要用 change proposal、dev verification、CR summary/evaluation 留下清晰审计链。
6. 当 review 工具降级为主上下文串行审查时，review record 必须披露 fallback 模式与剩余可信度风险。
