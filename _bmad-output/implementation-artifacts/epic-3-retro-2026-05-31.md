### Challenges（挑战）

- Full canonical package root coverage 继续影响 Epic 3。Story 3.2 的 CR 证明，仅校验总数、duplicate 或 module count 不足以证明 selected roots 完整；必须比较 expected root set 与 actual skill-index root set。
- Public JSON path/redaction 风险重复出现。Story 3.1 暴露 status path projection 泄漏风险，Story 3.6 又暴露 `ValidationIssue.affectedPath` guard 缺口；后续 public path 字段必须默认复用同一 policy。
- Artifact path 与 legacy validation 的 production 聚合路径比 rule helper 测试更容易漏。Story 3.4 多轮 CR 表明，直接测 helper 不等于 command-level validation 已覆盖。
- Story 3.5 的 HALT 是正确的。缺少 `src/commands/update.ts` 和 CLI `update` / `update --repair` 注册时，直接在 JSON contract Story 中造孤立 scaffold 会破坏 Story 顺序与范围边界。
- `_bmad-output/project-context.md` 仍是占位文件。Epic 3 实际 guardrails 来自 Story、PRD、Architecture、owning SPEC、CR 记录和源码，不应把 project-context 占位内容当作实现真源。
- 工作树存在大量既有未提交改动。Epic 3 各 Story 记录都强调只处理当前 Story 范围；这是必要的防扩散约束。

### Key Lessons（关键经验）

1. `status` 的空 `issues` 不等于安装健康通过；安装健康必须读取 `data.highLevelHealth`。
2. `validate` 是 local-only、read-only diagnostic command；它可以发现 drift，但不能自动修复或重写文件。
3. `CommandResult` / `ValidationIssue` 是 public JSON 的唯一语义入口；human-readable output 只能渲染这些语义，不能另造自动化字段。
4. Path policy 必须前移到 schema、projection、sorting 和 renderer 共同使用的 shared guard；不能只在某个 reporter 层做补救。
5. Full canonical inventory 必须按 package root set equality 证明，不能用 representative subset、module count 或 help/menu metadata 代替。
6. Blocking CR finding 留在 fixer loop 中解决；CR TODO backlog 只接收真正非阻塞、可延期且未解决的改进项。
