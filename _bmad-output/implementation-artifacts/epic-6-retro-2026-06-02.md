### Challenges（挑战）

- Fixture contract 一开始容易退化为 snapshot 比对。Story 6.1 的 CR 暴露了 object key ordering、non-stable field allowlist 和 expectedOutputClass registry 绑定问题，说明 comparator 必须由 owning schema/parser 管理。
- Existing update 的 apply result 与 installed-state projection 容易分裂。Story 6.2 证明如果 files-index 不随安全 apply 同步，下一次 update 会把刚应用的 installer-owned 更新误判为 drift。
- Resolve parity 的 failure semantics 需要外置且可审阅。Story 6.3 的 required layer `layerRole` 错标说明 fixture expected stderr JSONL 必须和 runtime resolver / owning SPEC 同步，而不是作为孤立文本存在。
- Path portability gate 最容易出现“看起来有 expected output，实际上没有执行真实路径”的假阳性。Story 6.4 经过多轮 CR 才把真实 CLI、path escape、unsafe overwrite、terminal width、exit code 和 package inventory 串起来。
- Packaging acceptance 与 build order 存在流程耦合。Story 6.5 CR 指出 `release:packaging-check` 依赖已完成 build，但脚本或 package lifecycle 尚未固化串行入口。
- CR TODO backlog 与实现证据需要收口。Epic 6 已实质处理部分 Epic 5 带入风险，但 backlog 文件仍保留 `TODO-001`、`TODO-002`、`TODO-003` open，并新增 `TODO-005` 至 `TODO-008`。

### Key Lessons（关键经验）

1. Release confidence fixture 必须执行真实 command path 或明确证明 expected artifacts 与真实状态绑定；只读取手写 snapshot 不能证明 MVP control plane。
2. Stable comparison 只能排除 owning schema 显式声明的不稳定字段；timestamp、duration、random/process id、环境文本和 stack trace 不能靠字段名宽松放行。
3. Normal update 与 explicit repair 必须持续分离。normal update 只处理 non-conflicting installer-owned planned updates；repair output 必须走 `update.repair` data contract。
4. Source integrity fixture group 要保持 sub-case 独立，否则 trustStatus、write boundary、redaction 和 unreadable source failure 会混成难以定位的大 fixture。
5. Packaging manifest 必须与真实 `npm pack --dry-run --json` inventory 对齐，并把 packaged documentation examples 与 release gate fixtures 分类清楚。
6. Skill artifact loop 的 MVP 范围是 installed discovery、installed runtime support、metadata artifact 和 deterministic validation，不是 LLM workflow 质量评分或 Post-MVP governance。
