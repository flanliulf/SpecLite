### Challenges（挑战）

- Functional anchor 标准一开始不稳定。Story 2.1 曾因缺少独立 `skill-index.ts` / `help-index.ts` / `files-index.ts` / `phase-coverage.ts` 文件触发 HALT，后续通过实际代码和 tests 确认集中式 `manifest-generator.ts` / `runtime-structure.ts` / `target-writer.ts` 才是有效 anchor。
- SR 首轮发现跨 Story release-gate 归属冲突，说明 Epic 2 的 Story boundary 高耦合，必须靠 design review 先收口。
- 多轮 CR 都出现 `Agent` 子代理不可用时的单上下文降级审查。记录中已披露该降级，但它降低了交叉审查独立性。
- Story 2.4 和 2.5 都留下 P2 非阻塞项，集中在 fixture 可审阅性和 metadata contract 精度，而不是核心 runtime behavior。
- Story 2.5 末期暴露 `skillCount=54` vs fixture `53` 的 fresh-install fixture drift。Evaluator 明确判断它不属于 Story 2.5 artifact-path CR scope，但它会影响后续对全量 `npm test` 的解释。

### Key Lessons（关键经验）

1. Functional anchor 判断必须基于 executable contract、runtime write path 和 tests，而不是只基于期望文件名。
2. Release gate 归属要在 SR 阶段先切清楚；前置 Story 只能验证自己的边界，不能伪造后续 Story 才拥有的成功条件。
3. `artifactContract`、phase coverage、activation target、resolver output 和 artifact metadata 都必须只有一个语义真源。
4. Installed entry identity 需要从 `canonicalSkillId` 一路保持到 target directory、activationTarget、customization lookup key 和 `sourceSkill` metadata。
5. Fixture 是 release gate，不是装饰性示例；case 内联在 helper 中会降低审阅和复用能力。
6. Non-blocking TODO 必须明确归属。`generatedAt` contract 和 `skillCount` drift 的处理边界被记录清楚，避免 CR fixer 无授权扩范围。
