### Challenges（挑战）

- Lock acquisition timing 在 SR 阶段就暴露过规划不一致。Epic 4 证明 write-capable command 的时序必须前置为 read-only preflight 后获取 lock，再进入 safe planning / confirmation / apply。
- `update` / `repair` 的 public JSON 投影容易把内部分类误写成自动化契约。Story 4.5 的 unknown ownership projection 缺陷说明 `data.conflicts[]` 与 `updatePlan.actions[]` 不能随意互相映射。
- Safe-write 的失败语义比 happy path 更难。Story 4.4 的 CR 证明 partial failure、cleanup failure、nested stale temp 和 existing overwrite baseline 都必须有 stable issue 和 changed path 记录。
- `sourceDescriptor` 从 Epic 4 中段开始成为 update plan 的 blocker。缺失或 malformed descriptor 不能被当作普通 skip；这直接为 Epic 5 的 source integrity 工作埋下依赖。
- 默认 `npm test` 的 5s timeout 曾被记录为慢测治理风险。Round 4 未复现，但 `TODO-003` 仍需在 Epic 6 release confidence / 测试稳定性治理中处理。
- `_bmad-output/project-context.md` 仍是占位文件。Epic 4 的真实 guardrails 主要来自 Story、SR、CR、owning SPEC、源码和 tests，不能把 project-context 占位内容当作实现真源。

### Key Lessons（关键经验）

1. Protected classifier 结论必须优先于 files-index ownership；`unknown` 也是保护性状态，不能被默认解释为 installer-owned。
2. 普通 `speclite update` 的安全默认值是 non-overwrite；drift、不确定 ownership、缺少 source evidence 或 IDE mirror mismatch 都应先进入 conflict。
3. `update --repair` 只能处理可证明可恢复的 installer-owned drift；每个 repair action 必须有 `expectedHash`，并在 apply 后做 postcondition 检查。
4. Lock、safe-write 和 source evidence gate 是写入链路的一组共同前置条件，不应被各 Story 局部绕开。
5. Public `CommandResult` 中 command-level issue 与 path-level detail 必须分层；一个 `update.conflicts` 汇总 blocker 足够，逐路径细节留在 `data.conflicts[]`。
6. CR TODO 只承接真实非阻塞事项；P1/P2 blocker 必须在 fixer loop 内闭合，不能为了推进状态下放到 backlog。
