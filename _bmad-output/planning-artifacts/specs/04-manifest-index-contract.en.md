# Manifest And Index Contract（清单与索引契约）

## Status（状态）

Accepted for MVP planning.

## Ownership（所有权）

This SPEC is the canonical contract for installed manifest and index files generated by SpecLite MVP.

It owns:

- Manifest, skill index, help index, files index, and minimum phase coverage matrix public fields.
- Schema version and compatibility policy for those installed files.
- Canonical target ordering and module ordering rules used by generated indexes.
- Hash and ownership projection rules used by validation and update protection.

PRD owns product intent. Architecture owns implementation mapping. If either conflicts with this SPEC, this SPEC wins.

## Implementation Anchor（实现锚点）

Implementation must provide `src/manifest/manifest-schema.ts` as the executable schema/parser anchor for manifest, skill index, help index, files index, and phase coverage projection. This module is not a second contract source; if it conflicts with this SPEC, this SPEC wins.

## Scope（范围）

Covered installed artifacts:

- `_speclite/_config/manifest.yaml`
- `_speclite/_config/skill-index.*`
- `_speclite/_config/help-index.*`
- `_speclite/_config/files-index.*`
- Any generated minimum phase coverage matrix embedded in or derived from manifest/index data.

MVP does not define a team governance dashboard, coverage percentage, trend report, or multi-project rollup. Those are Post-MVP and must consume this contract instead of redefining installed state.

## Source Of Truth（真源）

Source-side truth:

- Module metadata and source skill packages under `assets/source/speclite/` define canonical modules, canonical skill ids, source package content, phase metadata, help/menu labels, and default artifact contracts.
- Help index source data must reference canonical skill ids. It must not define a second skill identity.
- `_bmad-output/planning-artifacts/specs/05-ide-adapter-registry-contract.en.md` owns adapter ids, target ids, target order, and adapter capability semantics.
- `_bmad-output/planning-artifacts/specs/08-fixture-contract.en.md` owns fixture layout and release gate policy.

Installed projection truth:

- Manifest and indexes are the installed projection of selected modules, source descriptor, target IDEs, generated files, ownership, hashes, and discovery metadata.
- IDE mirrors are regenerated execution-plane projections. They are not canonical source.

## Schema Version（Schema 版本）

Every manifest/index artifact must contain a schema version field.

MVP versions:

- `speclite.manifest.v1`
- `speclite.skill-index.v1`
- `speclite.help-index.v1`
- `speclite.files-index.v1`
- `speclite.phase-coverage.v1`

Backward-compatible additive changes may add optional fields. Removing fields, renaming fields, changing field meaning, narrowing enum values, changing field types incompatibly, or adding required fields requires a new schema version.

## Canonical Target Identity（目标标识）

MVP IDE target ids are physical execution targets, not branded IDE claims:

- `claude`: `.claude/skills`
- `agents`: `.agents/skills`

GitHub Copilot and Cursor may use the `agents` target when they support `.agents/skills`. MVP must not fabricate `copilot` or `cursor` target ids unless a dedicated adapter exists.

Manifest/index projections must not render the `agents` target as branded Copilot/Cursor readiness; branding and dedicated target ids may only be introduced by a future dedicated adapter.

Canonical target order is owned by `_bmad-output/planning-artifacts/specs/05-ide-adapter-registry-contract.en.md`:

1. `claude`
2. `agents`

Manifest generation, command JSON `ideTargets`, validation `checkedTargets`, and fixture expected outputs must use this order. They must not use glob order, filesystem order, user selection order, or async adapter completion order.

## Minimum Phase Coverage Matrix（最小阶段覆盖矩阵）

MVP phase coverage is a deterministic installed-state matrix, not a governance score.

Each row must include:

```ts
type PhaseCoverageRow = {
  schemaVersion: "speclite.phase-coverage.v1";
  phaseId: string;
  phaseLabel: string;
  moduleId: string;
  canonicalSkillId: string;
  ideTargets: Array<{
    targetId: "claude" | "agents";
    entryPath: string;
    activationTarget: string;
    status: "mapped" | "unsupported" | "failed";
  }>;
  artifactContract?: {
    artifactType: string;
    defaultOutputPath: string;
    requiredMetadata: Array<"workflowType" | "sourceSkill" | "generatedAt">;
  };
};
```

Path fields must be project-relative POSIX paths. Rows sort by `phaseId`, then `moduleId`, then `canonicalSkillId`.

`artifactContract` validates the minimum artifact loop contract for a skill. MVP validation checks artifact type, default output path, and required metadata values. It does not judge artifact content quality, narrative completeness, or human review outcome.

Metadata value rules:

- `workflowType` must be a non-empty stable string.
- `sourceSkill` must be a non-empty stable canonical skill id.
- `generatedAt`, when present in an artifact, must be a canonical UTC ISO string in the millisecond UTC form produced by JavaScript `Date.toISOString()` and must be excluded from stable fixture snapshot comparison unless a fixture explicitly normalizes it.

## Artifact Contract Semantics（Artifact Contract 语义）

This SPEC owns the fields and minimum validation semantics for the MVP artifact contract. PRD, Architecture, CommandResult, and Epics may only reference this section; they must not define a second artifact contract.

`artifactContract.artifactType` is a stable artifact kind, not a human-readable title. `defaultOutputPath` must be a project-relative POSIX path and must live under `_speclite-output/` or the configured workflow artifact root.

The configured workflow artifact root is also a contract path: it must be a project-relative POSIX path, must resolve inside the target project boundary, and must not point outside the project through symlink escape or path escape. Boundary violations must be reported as `artifact-path.escapes-project` or `artifact-path.symlink-escape`; escaped absolute paths must not be written into public JSON, manifest/index, or fixture snapshots.

MVP validation only checks:

- artifact type matches `artifactContract.artifactType`
- output path matches `defaultOutputPath` or a configured project-relative path
- required metadata keys exist and have valid value ranges
- `workflowType` and `sourceSkill` are non-empty stable strings
- `sourceSkill` matches the installed canonical skill id
- `generatedAt`, when present, matches the canonical UTC ISO string / JavaScript `Date.toISOString()` millisecond UTC form and is normalized or excluded during stable fixture snapshot comparison

Artifact files are workflow-owned. Install, update, and repair must not treat workflow artifacts as installer-owned changed paths and must not use artifact validation results to trigger overwrite. MVP does not validate narrative quality, content completeness, human review conclusions, or business correctness.

Target status semantics:

- `mapped`: the adapter generated a self-contained skill entry for the target and the entry is visible in installed metadata.
- `unsupported`: the adapter declares that the target cannot represent this entry type or command pointer mode in MVP. This is not a write failure.
- `failed`: the adapter attempted or planned a mapping but target directory resolution, write, schema generation, or reverse validation failed.

Target status vocabulary is layer-specific. `mapped` / `unsupported` / `failed` belongs to installed phase coverage. Install planning uses `planned` / `unsupported` / `failed`; status summaries use `not-configured` / `configured` / `partial` / `failed`. These vocabularies must not be interchanged.

## Skill Index（Skill 索引）

The skill index maps canonical skill ids to source package metadata and installed target entries.

Required MVP fields:

- `schemaVersion`
- `canonicalSkillId`
- `moduleId`
- `sourcePackagePath`
- `canonicalPackageHash`
- `installedTargets[]`
- `phaseIds[]`

`canonicalPackageHash` is package-level. It validates that the same canonical package content is mirrored across IDE targets. It does not replace file-level hashes in the files index.

## Help Index（Help 索引）

The help index maps user-facing menu/help entries to canonical skills.

Required MVP fields:

- `schemaVersion`
- `phaseId`
- `entryLabel`
- `canonicalSkillId`
- `activationTarget`
- `targetIds[]`

Help index entries must reference `canonicalSkillId`. They must not create alternate skill ids, alias-only identities, or IDE-specific skill identities.

## Files Index（文件索引）

The files index owns file-level integrity and ownership projections for installed files.

Required MVP fields:

- `schemaVersion`
- `path`
- `ownership`: `installer-owned` | `human-owned` | `workflow-owned`
- `hash`
- `hashAlgorithm`: `sha256`
- `executable`: boolean
- `artifactKind`
- `sourceRef`

Package-level hashes validate canonical package equality. File-level hashes validate drift, update planning, repair planning, changed paths, skipped paths, and conflicts.

File hashes are computed over raw file bytes. Line endings, executable bit, file mode, symlink handling, and case-conflict checks are separate validation dimensions and must not be silently normalized into the hash. Runtime scripts and generated scripts must set `executable` explicitly so permission drift can be diagnosed without overloading content hash semantics.

Source canonical text files must use LF line endings. Installers must not rewrite canonical text line endings per platform. If a platform-specific script must be generated, it is a distinct generated file with its own files index entry and raw-byte hash.

`executable` records POSIX executable intent. On Windows, validation does not require POSIX chmod semantics, but the field still records script generation intent and supports cross-platform fixtures.

Volatile operation-control files such as `_speclite/.lock` and safe-write temporary files must not be recorded in the files index and must not affect stable files-index hashes. Validation may inspect their shape or stale state through dedicated issue categories.

Human-owned and workflow-owned files may be listed for protection, but automatic update and repair must not mutate them.

## Fixture Policy（Fixture 策略）

Manifest/index fixtures are contract tests, not documentation examples. This SPEC owns only manifest/index fields and projection semantics; fixture directory names, release gate classification, expected output classes, snapshot comparison rules, release checklist gates, and regression asset policy are owned by `_bmad-output/planning-artifacts/specs/08-fixture-contract.en.md`.

When manifest/index public fields, schema version, hash/ownership projection, or phase coverage semantics change, the corresponding fixture inputs, expected manifest/index snapshots, command JSON expected outputs, and validation assertions must be updated according to the fixture contract. Generated manifest/index outputs must be deterministic unless a field is explicitly declared by an owning SPEC and excluded from stable fixture comparison.
