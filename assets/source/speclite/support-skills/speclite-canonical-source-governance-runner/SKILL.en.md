[Overview]
    Execute the full canonical source governance workflow after the `canonical-source-change-check` hook detects `assets/source/speclite/` changes. This is not a read-only checker; it connects the governance map, impact matrix, human decisions, targeted edits, and verification commands into one implementation flow.

[Core Capabilities]
    - **Governance classification**: Read `assets/source/speclite/canonical-governance.json` and `docs/reference/canonical-source-governance.md`, and separate `D0`, `D1`, and `D2`.
    - **Impact matrix**: Use git diff to decide whether changes affect canonical source, module discovery, hook source, public docs, living legacy, frozen history, or release evidence.
    - **Hook follow-up**: Treat `canonical-source-change-check` warnings as a trigger for governance execution, not only for the read-only checker.
    - **Targeted edits**: When authorized, edit only files required by the impact matrix.
    - **Decision records**: Record `updated`, `skipped`, or `historical snapshot` for `D1` / `D2` surfaces so historical records are not mistaken for current truth.
    - **Verification closeout**: Run canonical checker warn / strict modes, relevant lint, focused tests, build, full tests, packaging check, and `git diff --check`.

[Workflow]
    This Skill uses a sequential workflow plus governance checks. Detailed steps, matrix, and stop conditions are in `references/canonical-source-governance-runner-workflow.md`.

    1. Read the governance map and governance reference.
    2. Read git diff / staged diff / untracked files, scoped to canonical source changes and related derived files.
    3. Build the impact matrix, handling `D0` first and `D1` / `D2` next.
    4. When edits are needed, update canonical source, docs, fixtures, tests, checker, or packaging manifest with targeted changes.
    5. Use `templates/decision-record.md` to record update or skip rationale for `D1` / `D2`.
    6. Run warn and strict checker modes plus relevant verification commands, then summarize.

[Notes]
    - This Skill is for maintaining SpecLite's own canonical source. It is not part of the default target-project SDLC runtime install set.
    - Local hooks remain warning-only; blocking behavior belongs in strict checker, CI, or release gates.
    - `D0` issues must be closed with file evidence and script output, not memory.
    - `D1` / `D2` issues require rationale. Do not silently rewrite old `PLAN.md`, `EXPERIMENTS.md`, or handoff snapshots as current truth.
    - When modifying support skills, do not add them to `core` / `sdlc` `module-help.csv` unless a product decision explicitly installs them in target projects.
