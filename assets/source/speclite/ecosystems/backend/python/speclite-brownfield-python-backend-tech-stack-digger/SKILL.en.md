# Speclite Brownfield Python Backend Tech Stack Digger

[Overview]
    Speclite Brownfield Python Backend Tech Stack Digger is a 1-analysis workflow for Python backend stack discovery. It follows the generic `speclite-brownfield-backend-tech-stack-digger` report contract while specializing in `pyproject.toml`, Poetry, uv, pip, Pipenv, Conda, FastAPI, Django, Flask, ASGI / WSGI, ORMs, task queues, cache, security, and testing facts.

[Core Capabilities]
    - **Python project discovery**: Identifies package layouts, monorepo services, `src/` layout, ASGI / WSGI apps, `manage.py`, Procfile, Docker, gunicorn, and uvicorn commands.
    - **Dependency version resolution**: Prefers `poetry.lock`, `uv.lock`, `Pipfile.lock`, pinned `requirements*.txt`, Conda locks, and `pip freeze` / `pipdeptree` facts.
    - **Runtime detection**: Extracts Python version evidence from `requires-python`, `.python-version`, runtime image, tox/nox, CI setup, and Conda environment.
    - **Framework detection**: Identifies FastAPI, Django, Django REST Framework, Flask, Starlette, Tornado, Sanic, Celery workers, and server entrypoints.
    - **Data and middleware analysis**: Detects SQLAlchemy, Django ORM, Tortoise ORM, Peewee, Alembic, psycopg, asyncpg, Celery, RQ, Redis, object storage, and HTTP clients.
    - **Security and engineering stack classification**: Detects Django auth, PyJWT, python-jose, Authlib, OAuthlib, Pydantic, OpenAPI, pytest, tox, coverage, logging, and observability.
    - **Evidence-linked Markdown output**: Generates a numbered checklist, evidence summary, unresolved items, and verification commands with `assets/python-tech-stack-report-template.md`.

[Workflow]
    This Skill uses a Python specific sequential analysis workflow. Packaging matrices, framework detectors, and version rules are in `references/python-tech-stack-workflow.md`.

    1. Parse user input and confirm `{project-root}`, `{output-dir}`, and `{report-name}`. If `{output-dir}` is missing, ask first.
    2. Read the generic report contract: output must remain compatible with `speclite-brownfield-backend-tech-stack-digger` sections and evidence rules.
    3. Scan Python project entrypoints: `pyproject.toml`, lockfiles, `requirements*.txt`, `Pipfile`, `environment.yml`, runtime version files, Dockerfile, CI pipeline, and service package.
    4. Prefer executable resolution: run `poetry show`, `uv pip list`, `pip freeze`, `pipdeptree`, or `conda list` depending on tooling. On failure, record the reason and fall back to lockfile / manifest parsing.
    5. Read runtime config and source entrypoints to fill framework, ASGI/WSGI server, database, Redis, MQ, scheduler, storage, auth, API docs, observability, and test facts.
    6. Merge facts and tag sources. `pyproject.toml` version specs are not installed versions; external server versions require deploy evidence.
    7. Write `{output-dir}/{report-name}`, defaulting to `python-backend-tech-stack.md`; final response includes path, key versions, and unresolved items.

[Notes]
    - This Skill only analyzes Python backend stacks; Java / Spring Boot, Node.js, Go, .NET, and other ecosystems should use their own specific Skills or the generic backend contract.
    - Lockfiles / pinned requirements are the highest-priority sources for actual dependency versions; `pyproject.toml`, `setup.cfg`, and `setup.py` ranges are declaration facts only.
    - Python runtime version must come from `requires-python`, runtime files, Docker image, Conda, tox/nox, CI, or user evidence, not dependency inference.
    - FastAPI / Starlette requires ASGI app or route evidence; Django requires settings / urls / manage.py / ASGI / WSGI evidence.
    - PostgreSQL Server, Redis Server, RabbitMQ Broker, S3 / MinIO Server, and other external server versions cannot be inferred from Python client versions.
    - Reports must include `Generated By`: `speclite-brownfield-python-backend-tech-stack-digger`.
