[Overview]
    An npm publishing Skill for open-source Node.js projects. It turns post-bugfix or post-feature delivery into one release workflow: version bump, fact audit, Chinese Conventional Commit, GitHub push, tarball smoke, local semi-automated publish, Claude/Codex hook guardrails, delayed verification, and incident recovery.

[Core Capabilities]
    - **Intent Gate**: Separate advice, readiness checks, preparation, publishing, and incident recovery; publish only after explicit `package@version` confirmation.
    - **SpecLite Release SOP**: Chain SemVer selection, `npm version --no-git-tag-version`, release gates, commits, push, publish, and delayed verification.
    - **Package Contract Audit**: Read package metadata, bin, exports, files, publishConfig, repository, homepage, bugs, engines, and scripts from real files.
    - **Registry And Version Gates**: Verify official npm auth, detect mirror registry confusion, check version occupancy, and never reuse published versions.
    - **Git Gate**: Enforce Chinese Conventional Commits, explicit staging, sensitive-file scanning, `origin/main` push, and clean-HEAD publishing.
    - **Release And Tarball Gates**: Prefer `release:check`, then verify real `npm pack` tarballs and clean CLI/library smoke tests.
    - **Hook Guardrails**: Define Claude/Codex blocking rules for publish, version bump, push, broad staging, and unsafe dist-tag changes.
    - **Postpublish Recovery**: Interpret publish output, verify metadata, dist-tags, clean `npx` or install, and handle propagation delay without republishing.

[Workflow]
    Use a sequential workflow with domain-specific gates. Load `references/speclite-npm-publisher-workflow.md` for detailed commands, decision rules, incident handling, and report templates; this entry keeps only phase routing.

    Step 1: Confirm Boundary And Authorization
        Classify the request. Before publishing, present target `package@version`, registry, publish command, validation plan, and current git state.

    Step 2: Establish Release Contract
        Read Contract Audit. Extract facts from `package.json`, build outputs, and git status. Stop on non-npm projects or unapproved `private: true`.

    Step 3: Plan Version And Run Prepublish Gates
        Choose SemVer, run `npm version <version> --no-git-tag-version` before commit, sync version-bound files, and run registry, version, metadata, build, test, and tarball gates.

    Step 4: Commit, Push, And Establish A Clean Publish Context
        Use Chinese Conventional Commits, explicit staging, and `origin/main` push. Publish only from clean `HEAD` or a clean worktree.

    Step 5: Publish Locally With Human Authentication
        Run publish after confirmation. Users enter password, security-key confirmation, and OTP in the terminal; the agent only parses output.

    Step 6: Verify And Report
        Check metadata, dist-tags, clean `npx`, or clean install. If write-side success exists but read-side lags, wait and retry instead of republishing.

[Notes]
    - Only edit user-authorized files; report metadata, README, LICENSE, bin, or script gaps before changing them.
    - Derive package names, versions, bins, entry files, and scripts from `package.json` and real files.
    - Never record passwords, tokens, OTPs, recovery codes, or browser auth secrets.
    - Validate remote packages from clean temporary directories, not the source repo root.
    - Never publish from a dirty worktree; tarball content must be committed and pushed first.
    - Never reuse published versions or change product requirements just to pass gates.
    - Hooks are deterministic guardrails only; they do not replace SemVer decisions, release reports, manual OTP entry, or postpublish judgment.
    - Write release reports to `.specskills/output/devops/speclite-npm-publisher/`, never the project root.
