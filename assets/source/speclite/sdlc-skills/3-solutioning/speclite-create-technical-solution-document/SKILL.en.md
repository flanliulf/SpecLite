[Overview]
    Synthesize PRD, UX, Architecture, Epics / Stories, Implementation Readiness reports, and project facts into a technical solution document for human review and delivery. The primary output is `{project_knowledge}/tsd/<requirement-id>-technical-solution-document.md`.

    This human-facing derived artifact does not replace PRD, Architecture, Story, or source contracts. It reports source conflicts and evidence gaps to the owning workflow instead of writing back.

[Core Capabilities]
    - **Evidence-grounded synthesis**: Separate `Confirmed`, `Proposed`, `TBD`, and `N/A`, and trace source versions, commits, or document status.
    - **Scope adaptation**: Tailor sections for a requirement, Epic, or cross-system change; prohibit empty sections and unexplained placeholders.
    - **Human-readable structure**: Lead with conclusions, then diagrams and details, including Executive Summary, Current / Target State, and an Applicability Matrix.
    - **Multi-system contract design**: Cover responsibility, protocol, authentication, timeout, retry, idempotency, error semantics, compatibility, data ownership, and owner.
    - **Mermaid diagram governance**: Select flowchart, sequence, state, class, or ER diagrams by question and limit diagram complexity.
    - **Quality and traceability validation**: Use a deterministic script to check metadata, sections, placeholders, Mermaid fences, traceability, and finalization conditions.

[Workflow]
    Read `references/workflow-details.md` for the complete workflow. Also read `references/document-structure.md`, `references/diagram-guidelines.md`, `references/multi-system-design-checklist.md`, `references/evidence-and-traceability.md`, and `references/quality-checklist.md` when their concerns apply.

    Step 1: Confirm requirement id, audience, delivery scope, and `Draft` / `Review` mode.

    Step 2: Discover and lock the input baseline. Finalization requires a current Implementation Readiness result that allows implementation; otherwise generate `Draft` only.

    Step 3: Build an outline from `assets/technical-solution-template.md`, explain conditional sections in the Applicability Matrix, and wait for outline confirmation.

    Step 4: Synthesize facts and proposals section by section, adding necessary Mermaid diagrams, multi-system contract tables, and Requirement → Design → Verification traceability.

    Step 5: Run `python3 scripts/validate_technical_solution.py <document> --mode draft|final`, with at most three check-fix-rescan rounds.

    Step 6: A final document may enter `Review` only. Set `Approved` only when the user or existing approval evidence explicitly authorizes it. Report the output path, status, source baseline, remaining risks, and next step.

[Notes]
    - SKILL.md is the Chinese canonical entry and SKILL.en.md is its equivalent English mirror. Version, YAML, capabilities, steps, constraints, and reference paths must remain aligned.
    - Output document prose is Chinese and section headings use the English（Chinese）form; commands, paths, field names, schema ids, APIs, protocol names, and proper technical terms remain in English.
    - Do not invent dependency versions, API fields, database structures, third-party responses, capacity numbers, or current implementation facts. Every `TBD` needs an owner, due date, and blocking impact.
    - Link full API schemas, DDL, and event definitions to their authoritative contracts; keep only change summaries, key semantics, and impact in the document.
    - A fixed path is a hard gate only when an owning SPEC requires it. Otherwise apply equivalent implementation policy and inspect `Contract Anchor -> Functional Anchor -> Evidence Anchor`; a `Guidance Anchor` is not a contract.
    - This Skill does not advance Story or Epic status. When consuming a `speclite-flow-gate` report, only `PASS` or `PASS_EQUIVALENT` is usable evidence; every other result remains a blocker.
    - Append `*本文档由 speclite-create-technical-solution-document Skill 自动生成*` to every output document.
    - PDF and Word export are not v1.0.0 capabilities. Markdown is the single content source; use a separate rendering workflow for format conversion.
