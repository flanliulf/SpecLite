[Overview]
    Turn PRDs, TSDs, Stories, implementation documents, code facts, or discussion conclusions into execution-ready QA test guides. The core principle is: do not write a development design document; help testers understand how to build data, how to trigger behavior, where to observe evidence, what counts as correct, and what must be treated as wrong.

[Core Capabilities]
    - **Testing mental model extraction**: Compress complex flows into the business rules, state semantics, and misinterpretation boundaries testers need.
    - **Test data setup guidance**: Define fields, fixtures, boundary values, negative inputs, and minimal data combinations.
    - **Trigger and evidence-chain design**: Connect APIs, jobs, configuration, DB records, reports, trace, logs, and external responses into reproducible execution paths.
    - **Scenario matrix generation**: For every scenario, output `Purpose`, `Data Setup`, `Trigger`, `Expected Result`, `Must Not Happen`, and `Evidence`.
    - **Rigor review**: Check accepted/finished confusion, vague wording, missing negative assertions, unlocatable evidence, and invented specifications.
    - **Readability control**: Write from the tester's point of view and avoid class-name dumps, architecture retelling, and non-executable generic statements.

[Workflow]
    This Skill follows an iterative workflow: fact inventory -> testing mental model -> guide draft -> rigor review -> final delivery. Read `references/speclite-qa-write-test-guide-workflow.md` for detailed steps, review rules, and output templates.

    Step 1: Inventory facts
        Read the user-specified documents, current specs, code facts, or discussion conclusions. Separate current facts, historical references, and unconfirmed items. Stop and ask for clarification when a critical business rule is missing.

    Step 2: Build the testing mental model
        Write the one-sentence rules testers must understand first, then list the main misinterpretation boundaries. For example, accepted is not finished, dry-run is not real write, and API failure must not create success mapping.

    Step 3: Generate the test guide
        Use `assets/test-guide-template.md` as the structural reference, then produce test data setup, trigger steps, evidence checklist, scenario matrix, pass/fail criteria, and troubleshooting path.

    Step 4: Review and fix precisely
        Use the review checklist in the workflow reference to confirm every scenario has positive expectations, negative assertions, and evidence locations. Replace vague wording and implementation-oriented phrasing.

    Step 5: Deliver
        Report the output path, scenario count, key coverage, review result, and remaining open questions. If writing a runtime artifact, append the generation marker at the end of the document.

[Notes]
    - First answer the five tester questions: what data to build, how to trigger, where to observe, what is correct, and what must be reported as wrong.
    - Do not write API accepted as business finished; do not use class names, module layers, or implementation call chains as the testing execution path.
    - Every key rule must include both a positive judgment and a negative judgment; express the negative judgment with `Must Not Happen`.
    - Evidence must be locatable through fields, tables, API responses, trace/report, logs, or external system responses; avoid non-executable words such as "normal", "reasonable", or "timely".
    - Do not guess unconfirmed third-party fields, enums, API responses, or environment configuration; mark them as open questions or ask the user to confirm.
    - Default output language is Chinese. Keep commands, paths, field names, fixture names, schema/issue ids, and other technical identifiers in English.
