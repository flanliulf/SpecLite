[Overview]
    This Skill writes and maintains open-source project `docs/` documentation. It treats `docs/` as the public documentation source for GitHub, npm, and future documentation sites, classifies content through Diataxis, and keeps README, package surfaces, indexes, and rendering constraints aligned.

[Core Capabilities]
    - **Repository evidence audit**: Read the real `docs/` tree, README, package metadata, CLI/API surface, and current style guide; when the project guide is missing, use the bundled style guide baseline.
    - **Diataxis classification**: Classify requests as tutorial, how-to, explanation, reference, or glossary work and write with the matching structure.
    - **Directory scaffolding**: Create or complete `docs/tutorials`, `docs/how-to`, `docs/explanation`, `docs/reference`, `docs/reference/glossary`, and related index pages.
    - **GitHub/npm-friendly writing**: Use CommonMark / GitHub Flavored Markdown and avoid Starlight-only admonition syntax.
    - **Index synchronization**: Update `docs/index.md` when documents are added, moved, or renamed; update README or preserve compatibility entries when package-facing paths change.
    - **Style guide curation**: Create and maintain `docs/_STYLE_GUIDE.md` with directory responsibilities, templates, validation goals, and docs tooling gaps.
    - **Quality validation**: Check document type boundaries, links, legacy entries, rendering constraints, target tooling statements, and boundaries for generalized content.

[Workflow]
    The detailed workflow lives in `references/write-opensource-docs-workflow.md`. The entry workflow is:

    1. Determine the mode: `assess`, `scaffold`, `write`, `migrate`, or `validate`.
    2. Read project facts: the `docs/` tree, `docs/index.md`, project `docs/_STYLE_GUIDE.md` or `references/docs-style-guide-baseline.md`, README, package metadata, and relevant source entrypoints.
    3. Choose the document type using `references/diataxis-doc-types.md`; ask the user when a high-impact classification is unclear.
    4. Generate or edit documents using the matching template from `assets/`.
    5. Synchronize indexes and compatibility entries so new documents are discoverable.
    6. Run available validation commands; only run `npm run docs:*` commands when they already exist in `package.json`.
    7. Summarize touched files, document types, missing tooling, and remaining risks.

[Notes]
    - `docs/` is the public project documentation source; it does not replace `_bmad-output/`, `_speclite-output/`, or `assets/source/speclite/`.
    - Reference answers "what is it, what are the fields, how do I invoke it"; Explanation answers "why, how does it work, what are the tradeoffs".
    - Tutorials are complete learning paths for beginners; How-To guides solve specific tasks for users with existing context.
    - The current rendering targets are GitHub and npm, so callouts use blockquotes such as `> Note:`, `> Tip:`, and `> Caution:`.
    - Style guide priority is project `docs/_STYLE_GUIDE.md` > this Skill's bundled `references/docs-style-guide-baseline.md` > explicit user instruction in the current turn.
    - Target docs tooling may be documented as a future standard, but must not be presented as an active gate until scripts exist in `package.json`.
    - General AI Coding essays or content not grounded in the current project should move outside project `docs/` or be marked as external reference.
