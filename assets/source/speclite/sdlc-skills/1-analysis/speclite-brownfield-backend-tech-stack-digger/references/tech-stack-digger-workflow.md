# Tech Stack Digger Workflow

## Overview（概述）

本文定义 `speclite-brownfield-backend-tech-stack-digger` 的详细执行规则。入口文件只保留阶段摘要；执行时按需读取本文。

## Inputs（输入）

| 参数 | 必需 | 说明 |
|---|---:|---|
| `{project-root}` | 是 | 目标既有项目根目录；未显式提供时使用当前 workspace root。 |
| `{output-dir}` | 是 | Markdown 报告输出目录；缺失时必须询问用户。 |
| `{report-name}` | 否 | 输出文件名，默认 `backend-tech-stack.md`。 |
| `{focus}` | 否 | 可限定为 `backend`、具体语言生态或具体模块；未提供时优先分析后端入口。 |

## Evidence Precedence（证据优先级）

1. 锁定或解析后的依赖事实：lockfile、resolved dependency graph、SBOM、依赖树、工具链解析结果。
2. 构建与包管理声明：manifest、workspace config、module config、parent baseline、framework baseline、dependency constraints。
3. 运行配置：应用配置、环境模板、secret 模板、feature flags、connection settings。
4. 部署配置：`Dockerfile`、`docker-compose.yml`、Helm chart、Kubernetes manifest、CI pipeline、runtime image。
5. 源码事实：启动入口、框架 bootstrap、imports、decorators / annotations、configuration classes、client factory、repository / mapper / model / schema。
6. 数据库脚本：`db/`、`migrations/`、DDL、schema migration 工具目录。
7. 文档与历史材料：只能作为候选线索；必须被前六类证据交叉验证。

## Ecosystem Routing（生态路由）

1. 先识别语言生态与后端入口，不直接套用任何生态规则。
2. 若用户只要求通用报告，使用本文的 Evidence Precedence 和 Category Matrix 生成跨生态清单。
3. 若识别到明确生态且用户需要精确版本解析，优先交给专属 Skill：
    - Java / Spring Boot：`speclite-brownfield-java-springboot-backend-tech-stack-digger`
    - Node.js：建议后续使用 `speclite-brownfield-nodejs-backend-tech-stack-digger`
    - Python：建议后续使用 `speclite-brownfield-python-backend-tech-stack-digger`
4. 专属 Skill 的结果仍必须使用本 Skill 的报告契约：编号清单、证据摘要、未确认项、核验命令和 `Generated By（生成来源）`。

## Category Matrix（分类矩阵）

| 类别 | 常见证据 |
|---|---|
| 开发语言 | source extensions、toolchain、runtime declarations、CI / container runtime |
| 运行环境 | runtime version files、runtime image、toolchain config、CI setup |
| 包管理 / 构建工具 | package manifest、build file、workspace config、lockfile |
| 核心框架 | framework dependency、bootstrap entrypoint、routing / controller markers |
| Web/API Server | embedded server、ASGI / WSGI / HTTP server、gateway adapter、runtime command |
| 数据库 | driver / client dependency、connection config、migration dialect、DDL syntax |
| 连接池 / Client Pool | pool dependency、client factory、connection settings |
| 消息队列 | MQ client dependency、consumer / producer config、broker endpoint config |
| 本地缓存 | in-process cache dependency、cache factory、cache annotations / decorators |
| 分布式缓存 | Redis / Memcached client、endpoint config、lock / lease utility |
| 数据访问 | ORM、query builder、repository、mapper、schema model、migration tool |
| 任务调度 | scheduler dependency、job entrypoint、cron config、worker command |
| 文件存储 | object storage SDK、filesystem adapter、endpoint / bucket config |
| 工具类库 | serialization、mapping、HTTP client、validation、date/time、crypto libraries |
| 安全认证 | auth framework、JWT / OIDC / OAuth dependency、middleware / guard / filter |
| API 文档 | OpenAPI / Swagger dependency、schema generator、docs route config |
| 观测治理 | metrics、tracing、logging、healthcheck、rate limit、circuit breaker |
| 测试框架 | unit / integration / API test dependencies and commands |

## Conflict Rules（冲突处理）

- 同一组件多个版本同时出现时，优先写解析后的实际版本，并在证据摘要列出 direct declaration。
- 根构建文件与模块构建文件冲突时，以目标后端模块实际解析结果为准。
- 文档声明与代码事实冲突时，以代码事实为准，并在 `Unconfirmed（未确认项）` 中列出冲突。
- 外部服务端版本没有部署证据时，不得从 client version 推断 server version。
- 无版本声明但通过框架基线、parent baseline、lockfile 或 constraints 间接引入时，写明解析来源；如果无法解析则写 `版本未在仓库中确认`。

## Output Requirements（输出要求）

报告必须包含以下章节：

1. `Backend Tech Stack（后端技术栈）`：编号清单，格式接近用户给定样例。
2. `Evidence Summary（证据摘要）`：表格列出组件、版本、证据路径、解析方式。
3. `Unconfirmed（未确认项）`：列出外部服务端版本、冲突事实、命令失败原因。
4. `Verification Commands（核验命令）`：列出实际执行或建议执行的命令。
5. `Generated By（生成来源）`：固定写 `speclite-brownfield-backend-tech-stack-digger`。

## Stop Conditions（停止条件）

- `{output-dir}` 缺失且用户未补充。
- 目标输出文件已存在，且用户未授权覆盖、追加或改名。
- 构建文件无法读取，且仓库没有足够配置或源码证据支持技术栈结论。
- 用户要求写入受保护目录，但当前环境没有写权限。
