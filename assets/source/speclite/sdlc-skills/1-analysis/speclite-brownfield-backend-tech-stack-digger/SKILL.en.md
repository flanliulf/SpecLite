[Overview]
    Speclite Brownfield Backend Tech Stack Digger is a 1-analysis backend stack report contract. It is not bound to Java, Node.js, Python, or any single ecosystem; it defines how to extract stack facts, tag evidence, and write a report to the user-specified output directory.

[Core Capabilities]
    - **Parameterized output directory**: Parses `{output-dir}` and optional `{report-name}`, defaulting to `{output-dir}/backend-tech-stack.md`.
    - **Repository and module discovery**: Identifies monolith, multi-module, monorepo, service directories, and backend entrypoints.
    - **Code-fact extraction**: Reads build declarations, dependency locks, runtime config, deployment config, migrations, source entrypoints, and framework markers; historical docs are candidate leads only.
    - **Version resolution precedence**: Prefers lock files, resolved dependency graphs, runtime images, and toolchain declarations; direct dependency declarations are secondary; unresolved facts are marked unknown.
    - **Stack categorization**: Outputs language, runtime, package/build tool, Web/API framework, Web server, database, MQ, cache, data access, scheduler, storage, security/auth, observability, and tests.
    - **Evidence and uncertainty tagging**: Adds source notes for key versions and marks unproven external server versions as requiring operations confirmation.
    - **Markdown report generation**: Uses `assets/tech-stack-report-template.md` to produce a checklist report with evidence and unresolved items.

[Workflow]
    This Skill uses a sequential analysis workflow. Detailed evidence matrices, version rules, and output constraints are in `references/tech-stack-digger-workflow.md`.

    1. Confirm `{project-root}`, `{output-dir}`, and `{report-name}`. If `{output-dir}` is missing, ask first and do not write to the project root by default.
    2. Create or confirm `{output-dir}`. Default report name is `backend-tech-stack.md`; if the target exists, do not overwrite without user authorization.
    3. Scan repository structure, language ecosystem, and build entry points. If an installed ecosystem-specific Skill can provide more precise resolution, prefer that Skill; otherwise use the generic evidence rules.
    4. Read runtime config and source evidence for database, Redis, MQ, scheduler, storage, security, service discovery, gateway, observability, and tests.
    5. Merge facts by evidence precedence. On conflicts, keep candidates with sources; never guess production runtime versions.
    6. Generate Markdown with `assets/tech-stack-report-template.md`: numbered checklist first, then evidence summary, unresolved items, and verification commands.
    7. Verify output existence, title, checklist, and evidence anchors; final response includes path, key findings, and unresolved items.

[Notes]
    - This Skill analyzes and generates documentation only; it does not modify business source, build config, or runtime config.
    - Code facts override README files, historical plans, conversation memory, and recollection; document facts require code/config/source validation.
    - External service versions require deploy evidence such as config, Compose, Helm, scripts, or pinned images; client versions do not prove server versions.
    - Ecosystem-specific version sources must be labeled precisely, such as lockfile, resolved dependency graph, constraints file, runtime image, or internal framework baseline.
    - Reports must include `Generated By`: `speclite-brownfield-backend-tech-stack-digger`.
    - If the user asks to update `_speclite/tech-stack.md`, first confirm it is the target output file.
