# Runtime Layout（运行时目录结构）

本文记录 SpecLite 安装到目标项目后的 runtime layout、installed projections、ownership 边界和 hook / agent descriptor。它回答“目标项目里会出现哪些 SpecLite 文件，以及谁可以管理它们”。

## Default Layout（默认布局）

默认安装会在目标项目中写入以下路径：

| Path | Ownership | Purpose | Commit Guidance |
|---|---|---|---|
| `_speclite/config.toml` | `installer-owned` | 项目共享 runtime config，包含 core / module config、Agent descriptors 和 Hook descriptors。 | 提交。 |
| `_speclite/config.user.toml` | `installer-owned` | 本地用户安装回答，例如 `user_name` 和 `communication_language`。 | 不提交；installer 已写入 `.gitignore`。 |
| `_speclite/custom/config.toml` | `human-owned` | 团队级 customization 覆盖。存在时 installer 不覆盖。 | 提交。 |
| `_speclite/custom/config.user.toml` | `human-owned` | 个人 customization 覆盖。存在时 installer 不覆盖。 | 不提交；installer 已写入 `.gitignore`。 |
| `_speclite/_config/manifest.yaml` | `installer-owned` | installed manifest 和 runtime path contract。 | 提交。 |
| `_speclite/_config/files-index.json` | `installer-owned` | installed files、hash、ownership、sourceRef 和 artifactKind 索引。 | 提交。 |
| `_speclite/_config/skill-index.json` | `installer-owned` | 已安装 Skill mirror 索引。 | 提交。 |
| `_speclite/_config/help-index.json` | `installer-owned` | module help / menu projection。 | 提交。 |
| `_speclite/_config/phase-coverage.json` | `installer-owned` | SDLC phase coverage projection。 | 提交。 |
| `_speclite/scripts/*` | `installer-owned` | legacy compatibility resolver scripts。默认 Skill activation 使用 `speclite resolve`。 | 提交。 |
| `_speclite/hooks/*` | `installer-owned` | installed hook runners 和 hook metadata。 | 提交。 |
| `_speclite/.lock` | transient | 写入类命令执行期间持有的 project operation lock，正常结束后移除；残留时由 `operation-lock.stale-lock` 提示。 | 不提交；需手动加入 `.gitignore`。 |
| `_speclite/_config/.update-journal.json` | transient | recoverable update 的 journal，用于中断后幂等续跑，提交后移除。 | 不提交；需手动加入 `.gitignore`。 |
| `.claude/skills/*` | `installer-owned` | Claude Skill mirror projection。 | 提交。 |
| `.agents/skills/*` | `installer-owned` | Agents/Codex Skill mirror projection。 | 提交。 |
| `.claude/settings.json` | `installer-owned` when generated by SpecLite | Claude project hook config。已有文件会触发 conflict，不会被覆盖。 | 提交；个人设置写 `.claude/settings.local.json` 并忽略。 |
| `.codex/hooks.json` | `installer-owned` when generated by SpecLite | Codex project hook config。已有文件会触发 conflict，不会被覆盖。 | 提交；`.codex/` 下其余内容不提交。 |
| `_speclite-output/0-brainstorming-artifacts/*` | `workflow-owned` | Fresh default brainstorming artifact plane。 | 提交。 |
| `_speclite-output/1-analysis-artifacts/*` | `workflow-owned` | Fresh default analysis artifact plane。 | 提交。 |
| `_speclite-output/2-planning-artifacts/*` | `workflow-owned` | Fresh default planning artifact plane。 | 提交。 |
| `_speclite-output/3-solutioning-artifacts/*` | `workflow-owned` | Fresh default solutioning artifact plane。 | 提交。 |
| `_speclite-output/4-implementation-artifacts/*` | `workflow-owned` | Fresh default implementation artifact plane。 | 提交。 |
| `_speclite-output/5-devops-artifacts/*` | `workflow-owned` | Fresh default devops artifact plane。 | 提交。 |
| `_speclite-output/project-knowledge-base/*` | `workflow-owned` | Fresh default Project Knowledge plane。 | 提交。 |
| `docs/*` | `human-owned` / workflow-specific | Public Documentation plane；不等同于 fresh `project_knowledge` 默认目录。 | 提交。 |

## Version Control Guidance（版本控制指引）

安装态的提交边界以上表 Commit Guidance 列为准：installer-owned 与 workflow-owned 路径提交给团队共享，个人级配置、transient 状态和 IDE 个人文件不提交。

Fresh install 只向目标项目 `.gitignore` 写入两条 user config 规则（`_speclite/config.user.toml`、`_speclite/custom/config.user.toml`），并把 `.gitignore` 登记为 `human-owned`。此后人工追加规则不会触发 drift，update、repair 和 uninstall 也不会重写或删除它。推荐在安装完成后追加：

```gitignore
# SpecLite transient state
_speclite/.lock
_speclite/.speclite-tmp-*
_speclite/_config/.update-journal.json

# Claude Code personal state
.claude/settings.local.json

# Codex: keep only the SpecLite hook config
.codex/*
!.codex/hooks.json
```

`.codex/*` 只忽略目录内容，不忽略目录本身，因此 `!.codex/hooks.json` 的否定规则有效；它防御 Codex 以项目目录作为 `CODEX_HOME` 时把 `auth.json`、`sessions/` 等用户态文件写进项目树。`.gitignore` 不会把已跟踪文件移出版本库，规则必须先于首次 `git add` 生效。

`_speclite-output/` 下的七个 artifact root 在 fresh install 后是空目录，git 不跟踪空目录。从版本库 clone 的副本应先运行 `speclite validate`，缺失目录由 `speclite update --repair --yes` 重建。

## Config Files（配置文件）

`_speclite/config.toml` 是 installer-managed shared config，需要提交到目标项目仓库。它当前包含：

| Section | Source | Purpose |
|---|---|---|
| `[core]` | Core module config | `project_name`、`user_name`、`communication_language`、`document_output_language`、`output_folder`、`brainstorming_artifacts` 等共享配置。 |
| `[modules.sdlc]` | SDLC module config | `user_skill_level`、`analysis_artifacts`、`planning_artifacts`、`solutioning_artifacts`、`implementation_artifacts`、`devops_artifacts`、`project_knowledge` 等路径。 |
| `[agents.<agent-id>]` | `module.yaml` Agent roster | 安装时固化 Agent `module`、`team`、`name`、`title`、`icon` 和 description。 |
| `[hooks.<hook-id>]` | hook runtime descriptor | 安装时固化 hook 来源、保护目标、runner、events、platform configs 和 trust note。 |

只有 selected modules 会参与 `_speclite/config.toml`、Agent descriptors、Hook descriptors 和 `_speclite/_config/*` indexes 的投影。当前 default no-ecosystem install 会写入 `core` / `sdlc` 相关配置；selected ecosystem module 如果未来声明 config prompts，只能在该 module 被选择时写入对应配置。unselected ecosystem modules 不会因为 bundled source 存在而创建 config section、Agent descriptor、help row、phase row、files-index entry 或 IDE mirror。

`_speclite/config.user.toml` 保存本地用户配置，不应提交。当前主要保存：

- `[core].user_name`
- `[core].communication_language`
- `[modules.sdlc].user_skill_level`

> Note: Installer-managed config 不是长期手工编辑面。需要稳定覆盖时，使用 `_speclite/custom/config.toml` 或 `_speclite/custom/config.user.toml`。

## Customization Files（定制文件）

`_speclite/custom/*.toml` 和 `_speclite/custom/*.user.toml` 是 `human-owned`。SpecLite 可以读取它们解析 customization，但 install、update、repair 和 uninstall 不能把它们当作 installer output 重写。

| Path | Scope | Commit Guidance |
|---|---|---|
| `_speclite/custom/config.toml` | 团队级 | 通常提交。 |
| `_speclite/custom/config.user.toml` | 个人级 | 不应提交。 |
| `_speclite/custom/<skill>.toml` | Skill 团队级覆盖 | 通常提交。 |
| `_speclite/custom/<skill>.user.toml` | Skill 个人级覆盖 | 不应提交。 |

## Agent Descriptors（Agent 描述符）

Recent runtime config 会把 SDLC Module 的 Agent roster 写入 `_speclite/config.toml` 的 `[agents.<agent-id>]` section。七个 Agent 的 ID、persona 与 runtime 投影角色以 [`skills/agent-roster.md`](skills/agent-roster.md) 为唯一源定义。

Agent 的完整 persona、菜单和 activation 协议仍来自 installed Skill package 的 `SKILL.md` 与 `customize.toml`。Runtime descriptor 用于 installed config summary、customization 和工具可读索引。

## Hook Descriptors（Hook 描述符）

当前 installed hooks 由 hook registry 统一投影：

| Hook | Runtime Root | Protected Target | Events | Behavior |
|---|---|---|---|---|
| `flow-gate-enforcement` | `_speclite/hooks/flow-gate-enforcement` | `protected_skill = "speclite-dev-story"` | `UserPromptSubmit` | 在执行 `speclite-dev-story` 前检查 story-kickoff Flow Gate 通过证据，必要时阻断。 |
| `canonical-source-change-check` | `_speclite/hooks/canonical-source-change-check` | `protected_surface = "assets/source/speclite"` | `PostToolUse`、`Stop` | 在 canonical source 变更后 warning-only 提醒运行 `speclite-canonical-source-governance-runner` 和 `speclite-check-canonical-source-change`，永远 exit `0`。 |

每个 hook runtime root 都包含 `runner.mjs` 和 `hook-manifest.json`。`_speclite/config.toml` 的 `[hooks.<hook-id>]` descriptor 会记录 `module`、`source_skill`、保护目标、`runtime_root`、`runner`、`events`、`platform_configs` 和 `trust_note`。

`flow-gate-enforcement` runner 只读取 hook event JSON、installed `_speclite/config.toml` 和 `{implementation_artifacts}/flow-gates/<story-key>-story-kickoff-gate.md` 的 frontmatter metadata。该 metadata 必须使用 `schemaVersion: "speclite.flow-gate-report.v2"`，并声明 `handoffContractVersion: "speclite.story-kickoff-handoff.v1"`；legacy v1 report 会被阻断并要求重新生成。runner 不生成 Flow Gate report、不修改 Story，也不推进 `sprint-status.yaml`。

`canonical-source-change-check` runner 只读取 git diff / staged diff / untracked files 是否触及 `assets/source/speclite/`。触及时调用 support skill 的只读检查脚本并输出 warning JSON，提示先用 `speclite-canonical-source-governance-runner` 分类影响面和记录 D1/D2 决策，再用 `speclite-check-canonical-source-change` 收口；它不返回 `decision: block`，不使用 exit code `2`。

Claude config 生成到 `.claude/settings.json`，包含 `UserPromptSubmit`、`PostToolUse` 和 `Stop`。Codex config 生成到 `.codex/hooks.json`，使用 event-keyed `{"hooks": {"Event": [...]}}` 形态。已有 project hook config 会触发 manual action，installer 不覆盖。

Codex 项目 hooks 需要用户通过 `/hooks review` / `/hooks trust` 之类的本地信任流程后才会生效。SpecLite 文档应把 hooks 描述为 deterministic guardrail，而不是完整 workflow engine。

## IDE Mirrors（IDE 投影）

SpecLite 会把 canonical Skill packages 投影到 selected IDE targets：

| IDE Target | Mirror Path | Notes |
|---|---|---|
| `claude` | `.claude/skills/<skill-id>/` | Claude Skill package mirror。 |
| `agents` | `.agents/skills/<skill-id>/` | Agents/Codex Skill package mirror。 |

当前 default no-ecosystem install baseline 包含 19 个 core package roots 和 50 个 SDLC package roots。默认同时选择 `core` 和 `sdlc` 时，每个 selected IDE target 会获得 69 个 skill mirrors；这个数字只描述 default fixture，不是 selected ecosystem installs 的全局 truth。

技术生态扩展位于 `assets/source/speclite/ecosystems/<category>/<id>/`，例如 `ecosystems/backend/java-springboot/`。这些 ecosystem modules 是可选模块，依赖 `sdlc`，但不会在 `--yes`、`--json` 或无交互默认路径中自动安装。用户显式选择 `ecosystem-backend-java-springboot` 时，installer 会安装 `core`、`sdlc` 和该 Java / Spring Boot ecosystem module；未选择的 `ecosystem-backend-nodejs`、`ecosystem-backend-python` 不会出现在 `.claude/skills/`、`.agents/skills/`、`skill-index.json`、`help-index.json`、`phase-coverage.json` 或 `files-index.json`。

简而言之，selected module truth 决定 runtime projection：被选择的 ecosystem modules 进入 IDE mirrors 与 indexes，未选择的 ecosystem modules 保持 source-only。

Installed-state validation 以 `_speclite/_config/manifest.yaml` 中的 `installedModules` 和已生成 index 为 selected module truth。`validate`、`status`、`update` 和 `repair` 不从 bundled source 中的未选 ecosystem packages 推导目标项目应安装的内容；如果 index 中出现未选 ecosystem 的 sourceRef、moduleId 或 activation target，应视为 installed-state drift。

## Artifact Root（产物根目录）

默认 `core.output_folder` 是 `_speclite-output`。Fresh install 会在该 root 下投影七个 workflow-owned filesystem planes：

| Directory | Purpose |
|---|---|
| `_speclite-output/0-brainstorming-artifacts/` | Brainstorming session 与发散探索产物。 |
| `_speclite-output/1-analysis-artifacts/` | Product Brief、Research、PRFAQ 等 analysis 产物。 |
| `_speclite-output/2-planning-artifacts/` | PRD、UX、Epics 等 planning 产物。 |
| `_speclite-output/3-solutioning-artifacts/` | Architecture、Specs、implementation readiness 等 solutioning 产物。 |
| `_speclite-output/4-implementation-artifacts/` | Sprint、Story、Flow Gate、Review、QA、Retrospective 与 Quick Dev 产物。 |
| `_speclite-output/5-devops-artifacts/` | CI/CD、deployment 与 npm release 产物。 |
| `_speclite-output/project-knowledge-base/` | Brownfield baseline、长期项目知识和 TSD 等 Project Knowledge 产物。 |

`docs/` 是 Public Documentation（公开文档）信息架构，不是 fresh `project_knowledge` 默认目录。七个 plane 的 config key、默认值与用途以 [`workflow-artifact-layout.md`](workflow-artifact-layout.md) 的 Configuration Mapping 为唯一源定义。

这些 artifact 属于 `workflow-owned`。它们记录真实研发过程，不参与 install/update 覆盖，也不会被 uninstall 自动删除。
